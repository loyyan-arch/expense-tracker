# 年度统计交付与下一课

## 实现

GET /statistics/yearly?year=2026：认证后按当前用户和发生日期统计，年份 1～9998，返回全年整数分总额及固定 12 个月明细。空月补零，无数据库迁移，月度接口保持兼容。

前端新增 /statistics/yearly 受保护页面和导航入口，展示年度汇总与月表；包含年份校验、失败重试、响应结构校验和旧响应保护。进入页面重新获取数据，在账单页修改后再次进入年度页即可看到最新结果。

开发分支 feat/yearly-statistics 基于 feat/cartoon-ui 的 9b6451f，包含已有界面风格；提交只包含本模块与发布文件，不包含此前未提交的 README/学习清单。合入 dev 时需要明确该界面提交也在分支历史中，可先合并界面 PR，或在同一个发布 PR 中包含界面与年度统计。

## 发布安排：前后端 1.1.0

本次本地验证：sc Python 环境全量后端 70 项测试通过；前端 43 项测试通过；TypeScript 检查与生产构建通过；三个 Compose 文件合并校验通过。后端新增 12 项测试、前端新增 9 项测试。未执行服务器更新或浏览器人工验收，PR CI 结果另行记录。

阶段：代码与测试 → 本地提交 → 推送/PR 与 CI → 构建并导出新镜像 → 服务器导入 → 后端先发布 → 前端发布 → SSH 隧道验收。未实际部署前，不把本文当作服务器发布成功记录。

本地使用干净的、通过验收的提交构建。当前工作区尚有用户文档修改，不直接以脏工作区制作后端发布镜像；可先单独提交文档或创建指定提交的独立 worktree，构建目录及其源码提交必须记录。

在该发布工作目录先执行 frontend 下 npm ci、npm run test:unit -- --run、npm run build；回到根目录执行（Docker Desktop Linux 容器）：

```powershell
docker build --platform linux/amd64 -t expense-tracker:1.1.0 .
$yearlyReleaseRevision = git rev-parse HEAD
docker build --platform linux/amd64 --build-arg "VCS_REF=$yearlyReleaseRevision" -t expense-tracker-web:1.1.0 ./frontend
docker save -o E:\111\expense-tracker-1.1.0.tar expense-tracker:1.1.0 expense-tracker-web:1.1.0
Get-FileHash E:\111\expense-tracker-1.1.0.tar -Algorithm SHA256
```

根 Dockerfile 的后端镜像目前没有源码标签，因此另行记录后端镜像 ID 与源码提交对应关系。后端构建需要下载依赖，若网络失败先解决并重新验收，不复用旧镜像冒充新版本。

上传镜像 tar 及 compose.yearly.yaml 到服务器；只传配置文件，不覆盖真实 .env 或数据库。核对哈希后执行：

```bash
cd /opt/expense-tracker
docker load -i /tmp/expense-tracker-1.1.0.tar
docker compose -f compose.yaml -f compose.web.yaml -f compose.yearly.yaml config --quiet
docker compose -f compose.yaml -f compose.web.yaml -f compose.yearly.yaml up -d --no-deps --no-build --pull never api
```

后端重建有短暂停机，数据卷仍使用 expense_data。先确认 api healthy、127.0.0.1:8001/health 返回 ok，认证后年度接口正常，再执行：

```bash
docker compose -f compose.yaml -f compose.web.yaml -f compose.yearly.yaml up -d --no-deps --no-build --pull never web
docker compose -f compose.yaml -f compose.web.yaml -f compose.yearly.yaml exec web nginx -t
curl --fail --show-error http://127.0.0.1:8080/api/health
```

新 web 容器会重新解析 api 地址。未来管理 1.1.0 必须始终带三个 -f，遗漏最后一个会使用基础配置的 1.0.0。

通过既有 18080 SSH 隧道登录，检查年度入口、12 个月、负结余、空年份和双账号隔离，确认历史账单仍在。刷新后仍需登录是本版本原有行为，下一课再修改。

回退：保留两个 1.0.0 镜像；使用只有 compose.yaml 和 compose.web.yaml 的命令先更新 api，再更新 web，并显式 restart web 重新解析后端 IP。年度功能不涉及数据库迁移，回退应用不删除现有账单。不能使用 down -v。

## 下一课：保持登录（尚未实施）

建议先做一个易于解释的服务端会话方案，避免同时引入访问令牌与刷新令牌两套生命周期。

1. 明确行为：刷新保持；是否关闭浏览器后仍保持、会话有效期与退出范围由本课确定。不要把注册密码最小 7 位与会话天数混为一谈。
2. Alembic 增加 sessions 表：用户、随机会话凭证的哈希、创建/到期/撤销时间；不保存明文会话凭证。
3. 登录成功设置 HttpOnly Cookie，/auth/me 读取有效会话；退出接口撤销会话并清 Cookie。明确原 Bearer API 的保留或迁移策略，不能让旧 JWT 绕过预期的退出失效规则。
4. 前端初始化先请求 /auth/me，等待完成再执行需要身份的路由判断；网络异常与未登录分开处理。
5. Cookie 认证需要 CSRF 防护、SameSite 与生产 Secure 配置，HTTPS 验收另行完成；不保存用户密码到浏览器，也不把长期凭证放进 localStorage。
6. 用测试验证刷新恢复、超时、退出后旧凭证无效、跨账号/多标签页与服务重启。会话凭证撤销才是服务端退出，不能只清页面变量。
